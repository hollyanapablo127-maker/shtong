# 第一阶段：账户、基础权限与审计基线

- 状态：账户底座已实现；医保信息系统接入补充已确认
- 日期：2026-09-18
- 目标版本：`phase-1`
- 覆盖端：服务端、Web 用户端、Web 管理端、Android、iOS
- 不覆盖端：微信小程序

## 1. 阶段目标

第一阶段以身份与系统管理底座为主，并按已确认范围接入唯一业务模块“医保信息系统”；不开发课程、教学、消息或其他未定义业务模块。交付后应满足：

1. 系统管理员可以登录，在 Web、Android 和 iOS 上管理账户、授权和审计记录。
2. 教师管理员、学生管理员和普通用户可以登录；除当前授权的“医保信息系统”外，未定义业务工作台保持为空。
3. 非系统管理员首次登录，或密码被重置后的首次登录，必须先修改密码才能建立正常会话；具有 `USER` 身份的账户首次改密后还必须完善身份证号、手机号、现家庭住址和户籍地址，完成前不能进入工作台。
4. 系统管理员可以创建和导入账户、按选择或查询结果导出账户、重置密码、逻辑删除账户、将学生账户移入毕业生账户，并为账户分配角色和组织管辖上限。
5. 所有认证、读取、导入、导出、变更、授权和审计查询均形成服务端权威审计记录。
6. 退出登录后，浏览器历史或移动端返回操作不能恢复受保护页面；旧会话也不能继续调用接口。

本阶段建立的权限模型必须允许以后按模块增加 capability，而不修改账号模型或重新复制账户。

## 2. 术语与内置角色

本阶段统一使用“教师管理员”这一名称，包含此前描述的辅导员场景；技术代码使用 `TEACHER_ADMIN`。教师管理员当前只允许一个或多个年级管辖上限。若未来普通任课教师和辅导员需要不同能力，应新增角色模板或能力包，不复用显示名称猜测权限。

| 角色代码 | 显示名称 | 工作区 | 本阶段功能 | 管辖上限 |
| --- | --- | --- | --- | --- |
| `SYSTEM_ADMIN` | 系统管理员 | `SYSTEM_ADMIN` | 账户、授权、组织基础数据、审计 | 系统管理域 `GLOBAL` |
| `TEACHER_ADMIN` | 教师管理员 | `ADMIN` | 空工作台、个人中心、退出 | 任意多个 `GRADE` |
| `STUDENT_ADMIN` | 学生管理员 | `ADMIN` | 空工作台、个人中心、退出 | `COLLEGE`、`GRADE`、`CLASS` 任意组合多选 |
| `MEDICAL_INSURANCE_ADMIN` | 医保系统管理员 | `ADMIN` | 医保信息系统、个人中心、退出 | `COLLEGE`、`GRADE`、`CLASS` 任意组合多选 |
| `USER` | 普通用户（学生） | `USER` | 空工作台、个人中心、退出 | 本人 `SELF` |

一个自然人只对应一个账号，一个账号可以同时拥有多个角色。工作区用于组织体验，不是权限等级，也不代表角色继承。进入外部模块时，模块必须按当前 Shtong 工作区建立“当前有效身份”会话，不能把该身份写回为账号唯一角色。

## 3. 管辖上限与未来模块权限

系统必须区分两层概念：

- **角色管辖上限**：账号以某个管理员角色最多可以管理哪些学院、年级或班级。
- **模块业务授权**：账号在某个模块中可以执行什么动作，以及该动作实际覆盖管辖上限内的哪些范围。

首期先保存角色管辖上限。以后增加模块时，每一项业务 capability 都必须创建独立、可审计的 grant，并在同一 grant 中绑定不超过角色管辖上限的 scope。

```text
role assignment
|-- assignment scope ceiling[]       # 本阶段建立的账户管辖上限
`-- authorization grant[]            # 本阶段仅系统管理和自助能力；以后逐模块增加
    |-- capability[]
    `-- grant scope[]                 # 必须是 assignment scope ceiling 的子集
```

禁止把账号全部 capability 与全部 scope 分别合并后交叉匹配。已有学院、年级或班级管辖上限不会自动获得未来模块的查看、编辑、审批或导出权限。

## 4. 阶段范围

### 4.1 系统管理员功能

| 功能 | 基线行为 |
| --- | --- |
| 账户列表 | 分页、搜索、筛选、跨页选择；默认不展示逻辑删除账户 |
| 账户详情 | 查看基本资料、状态、角色、管辖上限、最近登录和授权历史摘要 |
| 添加账户 | 创建单个账户，选择角色、学生当前班级和管理员管辖上限 |
| 更正账户资料 | 可更正登录账号、姓名和学生可空性别；姓名允许重名，学工号永久不可修改 |
| 学籍变动 | 通过独立操作调整具有 `USER` 身份学生的当前班级，撤销旧会话并记录前后组织 |
| 批量导入 | 下载固定模板、上传、全量校验、预览结果、确认提交、下载结果 |
| 导出 | 有选择时导出所选账户；没有选择时导出当前查询条件命中的全部账户 |
| 重置密码 | 单个或批量重置，撤销目标账户现有会话；非系统管理员下次登录强制改密 |
| 删除 | 单个或批量逻辑删除，不物理删除账号、授权历史或审计证据 |
| 移入毕业生 | 单个或批量将符合条件的学生账户置为 `GRADUATED`，立即禁止登录并撤销会话 |
| 权限授权 | 分配/撤销角色，维护教师年级上限和学生管理员学院/年级/班级上限 |
| 组织基础数据 | 维护或导入学校、学院、年级、班级树，供成员归属和 scope 选择使用 |
| 审计查询 | 按时间、操作者、涉及账户、事件、结果和请求标识查询并查看脱敏详情；导出要求独立高风险控制 |
| 个人中心 | 列表查看并点击复制本人资料；敏感字段默认脱敏，密码复核成功后直接复制明文；通过独立页面主动修改密码；退出登录 |

### 4.2 其他账户功能

教师管理员、学生管理员和普通用户登录后包含以下固定动作；只有满足模块角色与范围时才显示医保入口：

- 空工作台；不得下发未开发业务模块的占位入口。
- 个人中心；以列表只读展示姓名、学工号和身份相关组织信息，所有展示值均可点击复制；身份证号、手机号、现家庭住址和户籍地址默认脱敏，点击后须用当前密码复核并直接复制，不在页面显示明文。
- 主动修改密码。
- 退出登录。

“医保系统管理员”登录后进入 `ADMIN` 工作区，可使用授权范围内的医保信息系统；其余管理工作区能力仍按具体角色和 capability 判断。

教师管理员和学生管理员可以建立管理员工作区，但本阶段没有任何业务 capability，所以空工作台不代表未来已有业务权限。

个人中心按有效角色组合展示：具有 `USER` 的账户一律视为学生，即使同时具有学生管理员等角色，也展示可空性别、学校/学院/年级/班级和对应辅导员；教师/辅导员展示管辖年级；学生管理员展示学院、年级或班级管辖范围；系统管理员展示全校系统管理范围。修改密码按钮进入独立页面，不在资料列表内嵌表单。

系统管理员可以更正登录账号、姓名、学生性别，以及学生本人已完成首次填写的身份证号、手机号和两处地址，姓名允许重名；管理员不得代替尚未完成首次资料填写的用户绕过强制流程。学工号创建后永久不可修改。学生班级不得通过基本资料更正，必须使用独立“学籍变动”操作并完整审计原班级、新班级、原因和操作者。敏感字段变更审计只记录字段、分类和有无变化，不记录明文。

首次资料完善使用国家地名信息库行政区划数据选择省、市、区/县，详细地址由用户填写；身份证执行18位格式、出生日期与校验位验证，手机号执行中国大陆手机号格式验证。该流程适用于所有具有有效 `USER` 身份的账户，包括兼任学生管理员的学生，且不能通过关闭页面、深链或客户端篡改跳过。

### 4.3 明确不做

- 微信小程序工程实现、接口联调和发布配置。
- 课程、实验、题库、审批、消息、业务报表等业务模块。
- 通用工作流引擎。
- 面向业务数据的统计、导出或管理员操作。
- 账户物理删除、审计记录修改或审计记录删除。
- 第三方社交登录、短信找回密码和公开注册。医保信息系统使用 Shtong 统一会话 SSO，不建立第二套密码登录。
- 动态自定义角色设计器；首期只使用五个内置角色模板。

### 4.4 当前模块：医保信息系统

本阶段唯一新增业务模块为“医保信息系统”。Shtong 只负责入口、统一账户、统一会话、角色/管辖范围映射和审计关联；模块业务页面、业务逻辑和数据库规则由对应业务系统维护，接入侧仅增加独立 SSO 适配层及认证/权限映射。

| Shtong 身份与上下文 | `_yb` 角色 | 进入条件 | 范围 |
| --- | --- | --- | --- |
| `SYSTEM_ADMIN` 工作区 | `super_admin` | Shtong 系统管理员已登录 | 系统全局 |
| `MEDICAL_INSURANCE_ADMIN` 的 `ADMIN` 工作区 | `admin` | 已登录且存在有效范围 | 学院、年级、班级任意组合并集 |
| `USER` 工作区 | `student` | 当前账号具有有效 `USER` 角色 | 仅本人 |

多角色账号默认进入 `USER` 工作区；进入管理员或系统管理员工作区需要显式切换，不需要额外验证码。模块票据只绑定当前 workspace、Shtong 会话和授权版本，不能由客户端声明角色或范围。

模块入口使用一次性 60 秒服务端票据交换。每次受保护请求都校验 Shtong 父会话；父会话退出、账号停用、授权版本变化或模块角色失效时立即拒绝。短时网络故障只允许适配层有限 grace，不能形成独立长期登录。模块“返回工作台”只清除模块本地会话并返回 Shtong，不撤销父会话；下一次进入必须重新交换一次性票据。生产地址由部署环境配置，不写入源码或文档。

医保模块的姓名、学工号、性别、学院、年级、班级、证件号码、联系方式和两处地址均由 Shtong 账户资料投影，模块表单只读展示，写入请求不得更新这些字段。模块侧不再提供密码修改和全局退出；密码与全局退出只在 Shtong 完成。移动端模块使用受限 WebView/WKWebView 承载远程页面，不启动外部浏览器，且只允许配置的模块域名和返回工作台动作。

## 5. 账户状态

账号生命周期与登录锁定分开建模，避免把密码输错锁定误认为毕业或删除。

### 5.1 生命周期状态

| 状态 | 可登录 | 说明 |
| --- | :---: | --- |
| `ACTIVE` | 是 | 正常账户 |
| `GRADUATED` | 否 | 已移入毕业生账户，保留身份、归属、授权历史和审计关联 |
| `DELETED` | 否 | 逻辑删除，仅保留在受控查询和审计中 |

状态变化规则：

- 移入 `GRADUATED` 或 `DELETED` 必须撤销全部会话、递增账户授权版本并记录原因。
- 只有当前具有 `USER` 角色且没有有效 `SYSTEM_ADMIN`、`TEACHER_ADMIN`、`STUDENT_ADMIN`、`MEDICAL_INSURANCE_ADMIN` 角色的账户可以移入毕业生。
- 禁止删除或毕业当前操作者自身。
- 禁止删除、毕业或撤销最后一个可用系统管理员。
- `DELETED` 是产品语义上的删除，不代表数据库物理删除；恢复或个人信息匿名化另行定义受控用例。

### 5.2 登录安全状态

| 状态 | 说明 |
| --- | --- |
| `NORMAL` | 没有安全锁定 |
| `TEMPORARILY_LOCKED` | 登录失败次数达到阈值后的临时锁定 |
| `MANUALLY_LOCKED` | 系统管理员或安全策略手动锁定 |

账号只有在生命周期为 `ACTIVE` 且登录安全状态为 `NORMAL` 时才允许登录。

## 6. 密码与首次登录

### 6.1 强制改密规则

- 新建或导入的非系统管理员账户，其密码凭据状态为 `TEMPORARY`。
- 非系统管理员被重置密码后，密码凭据重新进入 `TEMPORARY`。
- 使用临时密码认证成功后只建立 `PASSWORD_CHANGE_ONLY` 限制会话，只允许修改密码和退出登录。
- 修改成功后撤销限制会话，签发全新正常会话，再执行 bootstrap。
- 账号只要具有有效 `SYSTEM_ADMIN` 角色，即按用户要求不进入强制改密流程；系统管理员密码创建与重置仍是高风险操作，必须记录原因并执行必要的双人控制。
- 任何客户端都不能通过隐藏页面、直接输入 URL 或调用接口绕过 `PASSWORD_CHANGE_ONLY` 限制。

### 6.2 临时密码交付

- 推荐由服务端生成高强度随机临时密码，数据库只保存密码哈希。
- 单个创建/重置只在成功响应中显示一次临时密码；离开结果页后不能再次取回。
- 批量创建/重置通过短时、加密的结果文件交付，下载一次后立即清除，未下载的文件 24 小时后删除；幂等重放不会再次返回临时密码。
- 临时密码、正式密码和密码哈希不得写入普通日志或审计事件。

具体安全要求见 [会话、密码与退出安全基线](../standards/session-password-and-logout.md)。

## 7. 批量操作语义

### 7.1 选择集合

- 单个操作和批量操作使用同一命令模型；单个操作是目标集合大小为 1 的批量命令。
- 重置密码、删除和移入毕业生必须显式传入不可复用的内部账户 ID 列表，不接受“空选择即全部”。
- 只有导出支持“没有选择即全部”，且“全部”严格表示提交时当前筛选条件命中的完整结果集。
- 如果无选择且无筛选，导出当前账户视图允许访问的全部非逻辑删除账户；界面必须先显示数量并要求确认。

### 7.2 一致性

- 导入在确认前先完整校验；存在任一错误时不写入任何账户。
- 删除、毕业、授权和同步批量命令默认全成全败；任一目标不符合规则则整批拒绝。
- 导出按任务创建时冻结的查询条件和授权版本生成，文件内容不得因任务执行期间账户变化而静默扩大。
- 每个批量命令使用幂等键，重复提交不得重复执行。
- 每个目标账户都必须出现在审计主体清单或不可变 manifest 中。

文件格式与字段见 [账户导入导出规范](../standards/account-import-export.md)。

## 8. 组织基础数据规则

组织树固定为：

```text
SCHOOL
`-- COLLEGE
    `-- GRADE
        `-- CLASS
```

- 内部 ID 永不复用；名称和业务代码分开保存。
- 业务代码在同一节点类型和有效期内唯一。
- 教师管理员至少选择一个 `GRADE`，服务端和数据库都拒绝学院或班级节点。
- 学生管理员至少选择一个 `COLLEGE`、`GRADE` 或 `CLASS`，允许任意混合多选，按子树并集计算。
- 普通用户的当前组织归属以班级为叶节点，由组织树推导学院和年级。
- 删除组织节点不删除历史引用；存在活动成员、下级组织或授权时不得直接删除，必须先处理影响清单。删除后允许重新创建相同名称和组织编号。

## 10. 审计最低结果

本阶段至少记录：

- 登录成功/失败、强制改密、修改密码、重置密码、登出、会话撤销和锁定。
- 账户列表查询、详情查看、新建、导入校验/提交、导出申请/完成/下载。
- 逻辑删除、移入毕业生、角色分配/撤销、管辖上限变更。
- 组织节点读取和变更。
- 审计搜索、详情查看和审计导出本身。
- 所有允许、拒绝、成功和失败结果。

账户变更记录允许字段级前后差异，但密码与秘密字段只能记录“已发生变化”。批量事件必须记录实际目标集合，不能只记录筛选条件或数量。

详细架构见 [全链路审计追踪架构](../architecture/audit-trail.md)，本阶段事件目录见 `packages/contracts/audit-events/account-access-baseline.v1.json`。

## 11. 验收摘要

1. 全新非系统管理员使用临时密码登录，只能进入强制改密；改密后旧限制会话失效。
2. 系统管理员能在 Web、Android、iOS 完成全部账户管理流程，结果一致。
3. 教师管理员只能被分配多个年级；学生管理员可混合选择学院、年级和班级。
4. 给管理员设置管辖上限不会自动赋予任何未来业务 capability。
5. 有选择时只导出选择项；无选择时导出提交时筛选命中的全部账户，并显示确认数量。
6. 删除和毕业均立即阻止新登录并使既有会话失效，但数据库身份和审计引用仍存在。
7. 退出后使用浏览器后退、Android 返回键或 iOS 返回手势均不能恢复受保护页面。
8. 每项允许、拒绝、成功和失败操作都可通过 `request_id` 在审计中定位。
9. 审计写入失败时，受保护读取不释放数据，写操作不提交。
10. 小程序目录无任何本阶段实现变更。

阶段功能范围与安全边界以本文及对应 API、数据库和架构契约为准。
