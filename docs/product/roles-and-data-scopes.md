# 身份、角色与数据管辖范围

- 状态：已确认
- 日期：2026-09-15
- 当前实现说明：登录已改为仅账号密码，MFA/step-up 已移除；本文涉及 MFA/step-up 的内容为长期设计，不代表当前行为，见 [ADR-0005](../architecture/decisions/0005-password-only-login-and-incremental-persistence.md)。

## 1. 基本原则

系统面向三个身份空间及对应工作区：用户 `USER`、管理员 `ADMIN`、系统管理员 `SYSTEM_ADMIN`。工作区用于组织界面，不是可直接放行请求的角色，不是数值型权限等级，也不自动逐级继承。真正授权使用具体角色、capability 和 scope；审计查询还必须绑定同一 grant 的 dimension、组织范围和 field clearance。

一个自然人只建立一个账号；同一账号可以同时拥有多个角色。管理员或系统管理员同时具有用户角色时，可以在不同工作区之间切换，无需维护第二套账号或第二套用户数据。

所有客户端共用统一账号体系和同一套业务事实数据。用户端与管理端是不同的入口和授权上下文，不是不同数据库；服务端按模块划分 PostgreSQL Schema/表及数据库权限，避免任一模块直接拥有整库权限。

首期内置角色如下：

| 角色代码 | 身份空间 | 定位 | 默认数据范围 |
| --- | --- | --- | --- |
| `USER` | 用户 | 使用面向用户的业务功能 | 本人 `SELF` |
| `TEACHER_ADMIN` | 管理员 | 教师管理员业务管理（包含辅导员场景） | 一个或多个年级节点 |
| `STUDENT_ADMIN` | 管理员 | 学生管理员业务管理 | 学院、年级、班级任意组合多选 |
| `SYSTEM_ADMIN` | 系统管理员 | 账号、授权、组织主数据和审计管理 | 系统管理资源 `GLOBAL` |

系统管理员不自动继承业务审批或业务数据修改权限。系统管理员需要参与业务时，应给同一账号额外授予教师管理员或学生管理员角色，使操作目的和审计责任清晰。

人员类别按有效角色组合判断，不按“最高角色”覆盖：只要账户具有有效 `USER`，即视为学生并保留学生性别、当前班级和辅导员关系，即使该账户同时具有 `STUDENT_ADMIN`、`TEACHER_ADMIN` 或 `SYSTEM_ADMIN`。其管理员管辖范围另行展示和授权，不替代学生学籍。

所有具有有效 `USER` 的账户首次改密后均必须完善身份证号、手机号、现家庭住址和户籍地址；该本人资料门禁不因同时具有管理员角色而豁免。日常个人中心只显示脱敏敏感字段，当前密码复核仅授权复制本人单个字段，不扩大角色或数据管辖范围。

## 2. 职责矩阵

| 能力 | 系统管理员 | 教师管理员 | 学生管理员 | 用户 |
| --- | --- | --- | --- | --- |
| 登录、维护本人资料 | 当前账号 `SELF` | 当前账号 `SELF` | 当前账号 `SELF` | 当前账号 `SELF` |
| 创建、启用、停用、锁定、解锁账号 | 全部账号 | 无 | 无 | 无 |
| 重置认证方式、撤销会话 | 全部账号 | 无 | 无 | 本人受限操作 |
| 授予、变更、撤销角色及范围 | 有，受高风险控制 | 无 | 无 | 无 |
| 配置学院、年级、班级 | 有 | 只读业务所需部分 | 只读业务所需部分 | 只读本人相关部分 |
| 配置通用字典和字段选项 | 有 | 无 | 无 | 无 |
| 用户业务查询与操作 | 仅在另有管理员角色时 | 授权年级内 | 授权范围内 | 本人业务 |
| 审批、退回、转办 | 仅在另有业务授权时 | 能力及年级范围内 | 能力及授权范围内 | 仅提交、撤回等用户能力 |
| 统计查询和导出 | 系统运行统计，或另有业务授权 | 能力及年级范围内 | 能力及授权范围内 | 本人可见统计 |
| 查询和导出审计记录 | 按独立审计权限 | 默认仅本人操作，扩展需授权 | 默认仅本人操作，扩展需授权 | 默认不可用 |
| 修改或删除审计原记录 | 无 | 无 | 无 | 无 |

表中“有”仍代表服务端必须验证具体 capability、当前上下文、二次认证状态和目标资源，不能仅根据角色名称放行。

“系统运行统计”只包括账号、安全、会话、授权、组织配置和审计运行情况，不包括学生或其他业务数据聚合。系统管理员查看任何业务统计时，必须在同一账号上另有教师管理员或学生管理员授权，并按该授权的 capability 与 scope 过滤。

“全部账号操作”包括创建、编辑、绑定/解绑登录方式、重置认证、锁定/解锁、停用/恢复、撤销会话以及合规注销/匿名化。账号内部 ID、授权历史和审计证据不允许由系统管理员物理删除；法定保留期和 legal hold 优先。

## 3. 组织范围

首期组织层级按以下关系建模：

```text
学校
`-- 学院
    `-- 年级
        `-- 班级
```

- 学院范围覆盖该学院下属的年级和班级。
- 年级范围覆盖该年级下属的班级。
- 班级范围只覆盖该班级。
- 多个范围按 OR 取并集，不做学院和年级之间的笛卡尔组合。
- 完全相同的重复 scope 应拒绝保存；父子节点重叠时界面提示，但保留直接授权意图，计算有效范围时再去重。

学生管理员可以同时拥有多个学院、年级和班级范围。例如“学院 A + 年级 B + 班级 C”表示三个节点子树的并集。

教师管理员只能被授予 `GRADE` 类型节点，可以拥有一个或多个年级；服务端与数据库约束必须拒绝给教师管理员授予学院或班级节点。

系统管理员在授予 `STUDENT_ADMIN` 时可对学院、年级、班级做任意组合多选；在授予 `TEACHER_ADMIN` 时只能多选年级。授权界面可以辅助选择，但最终类型约束、节点真实性和授权上限必须由授权服务及数据库提交时约束共同保证。

## 4. capability 与范围必须绑定

管理员账号先通过角色赋予保存管辖上限，具体模块授权再由以下内容共同组成：

```text
角色赋予 + assignment scope ceiling
`-- capability 集合 + grant scope 集合 + 有效期 + 授权来源
```

ceiling 表示账号在该角色下的最大管辖范围，本身不授予未来业务权限。只有同一条有效 grant 中的 capability 和实际 scope 同时匹配目标操作，并且实际 scope 不超过所属 assignment 的 ceiling 时才允许访问。不能先合并账号的所有 capability，再合并账号的所有 scope，否则兼任角色会发生串权。审计查询还要求同一 grant 中的 `ACTOR/SUBJECT/RESOURCE` dimension、组织范围和字段 clearance 完整匹配。

示例：某账号以教师管理员身份在年级 A 拥有 `approval.decide`，以学生管理员身份在学院 B 只拥有 `student.read`。该账号不得使用教师管理员的审批能力处理学院 B 的任务。

首期只支持正向授权，不引入显式 DENY 规则。不同范围需要不同能力时，应建立多条授权。

## 5. 批量操作与组织变更

- 批量操作默认要求所有目标用户均在该 capability 的有效范围内，否则整批拒绝。
- 若业务明确允许部分成功，API 必须返回逐项结果，并为每个目标建立审计关联。
- 统计、搜索、导出和审批任务与普通列表使用同一范围校验，不能绕过。
- 用户业务记录应保存操作发生时的组织归属或范围快照，不能只根据用户当前班级反推历史权限。
- 移动学院、年级、班级节点可能扩大既有授权，执行前必须展示影响范围，确认后使授权缓存失效并记录完整审计。
- 删除组织节点不物理删除被历史业务或审计引用的数据；删除后不再出现在活动组织树中，但允许重新创建相同名称和组织编号。

## 6. 授权管理约束

- 授权记录包含授权人、原因、有效期、创建时间、撤销人和撤销原因，只撤销不物理删除。
- 教师管理员和学生管理员的角色赋予必须保存 assignment scope ceiling；以后增加模块时，每项业务 grant 的 scope 必须是该 ceiling 的子集，不能自动继承为全模块权限。
- 账号停用、角色或范围撤销、组织归属变化后立即递增账号授权版本并撤销高权限会话。
- 禁止管理员给自己提权。
- 创建或撤销系统管理员、修改自身权限必须由另一名系统管理员复核；应急情况下只能走预先定义、全程审计的 break-glass 流程。
- 禁止停用或撤销最后一个可用系统管理员；该保护不得通过普通审批绕过。
- 管理员和系统管理员工作区建立上下文时均要求 step-up 与 MFA，使用更短的高权限会话；系统管理员和高风险操作还要求满足更强的认证等级及双人复核规则。
- 小程序固定为用户身份空间；即使账号兼任管理员，也不能通过小程序令牌调用管理接口。

## 7. 审计追踪要求

- 所有到达服务端的认证、会话、上下文切换、授权判断、业务/数据读取、搜索、统计、导出、写入、审批、任务和审计访问，无论允许、拒绝、成功或失败，均产生服务端权威审计事件。
- 事件记录操作者及其会话/工作区、请求来源、目的或原因、命中的 assignment/grant/scope/策略版本、涉及主体与资源、结果、错误码及允许记录的字段前后差异。
- 批量或统计操作必须保存完整主体清单，或保存不可变加密 manifest 及数量/摘要；不能只记录“查询了某学院”。
- 业务写入与权威审计在同一本地事务提交；受保护读取在返回数据前持久化审计。权威审计不可写时，受保护操作关闭失败，不以普通日志代替。
- 审计原记录只追加、不更新、不删除；修正、legal hold、归档与审计查询本身继续产生新审计事件。
- 密码、Token、Cookie、验证码、密钥、文件正文和完整请求/响应不得写入审计，敏感字段按分类脱敏或只记录“发生变化”。
- 页面打开、按钮点击等纯客户端行为可进入独立遥测，但不能作为服务端已读取数据或已执行操作的审计证据。

详细实现见 [全链路审计追踪架构](../architecture/audit-trail.md)。

## 8. 登录后的模块

应用进入认证门。无有效会话时显示登录；存在有效会话时可按策略使用生物识别或本机凭据解锁。

管理员和系统管理员不会自动拥有用户工作区，只有显式 `USER` 角色才可进入。账号拥有多个工作区且包含用户工作区时默认进入用户工作区；没有用户角色时停留在工作区选择/认证门，完成所需 step-up 与 MFA 后才建立最低权限的有效管理上下文。

登录后由服务端返回可用工作区和模块代码：

| 工作区 | 首期模块类别 |
| --- | --- |
| 用户 | 个人资料、具体业务、申请与进度 |
| 管理员 | 业务管理、待办审批、授权范围内统计 |
| 系统管理员 | 账户管理、授权管理、组织与字典、审计查询 |

客户端只把已知模块代码映射到本地编译的页面，未知代码忽略；服务端不得下发任意 URL、类名或可执行代码。隐藏模块只改善体验，每次 API 请求仍须重新鉴权。

详细实现见 [统一身份与分级授权架构](../architecture/identity-and-authorization.md) 和 [权限与审计概念数据模型](../database/access-control-and-audit-model.md)。
