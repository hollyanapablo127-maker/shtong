# ADR-0004：第一阶段仅建设账户、基础授权与审计

- 状态：已采用
- 日期：2026-09-16

## 背景

项目需要先形成可复用的账号和权限底座，再逐步增加业务模块。第一阶段要求服务端、Web、Android 与 iOS 同步具备系统管理员账户操作和审计能力，并按已确认范围接入唯一业务模块“医保信息系统”；未定义业务仍保持为空，微信小程序暂不开发。

最新产品用语将原“辅导员管理员”扩展为“教师管理员”，但权限规则不变：只允许任意多个年级。医保模块使用独立的 `MEDICAL_INSURANCE_ADMIN` 身份，映射到外部 `_yb` 的 `admin` 角色；统一技术代码避免多个语义重叠的角色。

## 决策

1. 内置角色统一为 `USER`、`TEACHER_ADMIN`、`STUDENT_ADMIN`、`MEDICAL_INSURANCE_ADMIN`、`SYSTEM_ADMIN`。
2. `TEACHER_ADMIN` 的产品显示名为“教师管理员”，包含辅导员场景，只允许多个 `GRADE` 管辖上限。
3. 角色赋予增加独立的 `assignment_scope_ceiling`，表示账号在该角色下的最大管辖范围。
4. 管辖上限本身不授予未来业务权限。每个新模块仍需在同一 grant 中绑定 capability 与不超过 ceiling 的实际 scope。
5. 第一阶段暴露系统管理员的账户、授权、组织与审计模块，并在满足角色与范围时暴露“医保信息系统”；其他未定义业务模块目录为空。
6. 删除是不可登录的逻辑删除；毕业是独立生命周期状态，二者都保留身份和审计证据。
7. 非系统管理员首次登录或重置密码后使用受限会话强制改密；系统管理员按产品规则豁免该流程。
8. 导出在无选择时表示当前筛选结果全部，其他破坏性批量命令必须显式提供目标 ID。
9. 退出同时撤销服务端会话并清空客户端受保护导航根，不能依赖禁用返回键。
10. 小程序不参与本阶段实现和联调。

## 后果

- 新业务模块可以只增加 capability、grant、模块 exposure 和端侧 feature，不迁移账号主模型。
- 系统管理员可以先配置教师和学生管理员的管辖边界，而不会意外让其访问尚未发布的业务。
- 数据模型多一层 ceiling 校验，但授权意图更清晰，也能防止未来模块授予超出账号职责的范围。
- 所有客户端必须共享 API 和代码目录契约，但 Android/iOS 仍各自实现原生 UI。
- 历史文档中的 `COUNSELOR_ADMIN`/“辅导员”统一更新为 `TEACHER_ADMIN`/“教师管理员（包含辅导员）”；由于尚无业务数据，不需要兼容迁移。
