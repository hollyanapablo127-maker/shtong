# ADR-0002：统一账号与 capability-scope 联合授权

- 状态：已接受
- 日期：2026-09-15

## 背景

同一自然人可能同时是用户、教师管理员（包含辅导员场景）、学生管理员或系统管理员。学生管理员的数据管辖范围可以是学院、年级、班级的任意多选组合，教师管理员只按年级管辖。

## 决策

- 所有端共用一个账号与 PostgreSQL 业务事实库，不为用户端和管理端复制账号；模块通过独立 Schema/表和最小数据库角色隔离所有权。
- 使用 `USER`、`ADMIN`、`SYSTEM_ADMIN` 三个身份工作区；角色可以叠加但不数值继承。
- 内置角色为 `USER`、`TEACHER_ADMIN`、`STUDENT_ADMIN`、`SYSTEM_ADMIN`。
- 教师管理员和学生管理员的角色赋予保存账号级 `assignment_scope_ceiling`；它只限制最大管辖范围，不自动授予业务 capability。
- 角色赋予下建立一条或多条 `authorization_grant`，每条 grant 同时绑定 capability 集合和带 dimension 的 scope 集合；审计查询 grant 还绑定字段 clearance。
- 授权只有在同一 grant 内 capability、目标 scope 及其 dimension 同时匹配，且管理员 scope 不超过所属 assignment ceiling 时成立；审计查询还必须由该 grant 独立满足字段 clearance，不能跨 grant 拼接。
- 学生管理员允许学院、年级、班级节点多选并按子树并集覆盖；教师管理员只允许年级节点。
- 系统管理员默认拥有账户、授权、组织配置和系统运行审计能力，不自动继承业务审批权限；敏感解密、全局业务审计、导出和保留策略需额外审计能力包。
- 系统管理员的系统统计仅限账号、安全、会话、授权、组织配置和审计运行指标；业务聚合需要额外业务管理员 grant。
- 所有范围过滤下推到服务端和 SQL；客户端模块与筛选器不构成安全边界。
- 角色模板上限、scope 节点类型、grant 全组合完整性、审计字段 clearance 和有效期由授权服务及数据库提交时约束共同校验。

## 结果

- 同一账号无需重复注册或同步资料。
- 可以明确解释每次访问使用了哪条角色赋予、授权和范围。
- 避免兼任角色时把某角色的 capability 与另一角色的 scope 交叉组合。
- 授权表和测试用例比简单角色字段更多，但安全边界更稳定。
- 角色或范围变化必须递增授权版本并撤销高权限上下文。

## 不采用的方案

- 用户与管理员使用两套账号或两个数据库：造成身份和业务数据重复。
- 单个 `role_level` 数字：无法表达管理员类型、多角色兼任和数据范围。
- `is_admin` 布尔字段：无法表达操作能力、有效期和授权来源。
- 先合并全部权限再合并全部范围：会产生 capability-scope 串权。
- 只依靠前端路由、菜单或小程序无管理员入口：无法阻止直接调用 API。
